# 统一认证与应用管理

## 责任与生命周期

身份（issuer + subject）、密码和第三方登录由 pro Auth 管理。BFF 只保存身份关联、租户成员、应用及授权，身份字段不以邮箱为主键。

BFF 成员角色：admin、viewer。只有 enabled 成员可以进入平台。成员停用后，服务端每次请求都会拒绝业务访问，仍允许本人清除 BFF 会话。BFF 退出只删除本系统会话，不退出 pro。

应用状态：enabled true / false；管理员可双向切换，普通成员只读启用且有授权的应用。应用编码创建后不可更改；更新携带 version，避免覆盖其他人的修改。本阶段保留历史记录，不提供删除。

每个应用写入和授权变更都在数据库函数中再次检查管理员、租户及版本，并在同一事务记录审计事件。外部请求中的租户字段与租户请求头不授予权限。

## 登录与会话

1. BFF 服务端生成 PKCE verifier 和 state。state 和浏览器绑定值只保存哈希；verifier 加密保存在短期事务记录中。
2. BFF 服务端向 pro Auth OAuth authorize 取得授权页地址，验证其属于配置的 pro 授权入口，提取不透明请求 ID 后直接打开统一登录表单。普通访问不经过 BFF 登录介绍卡片。
3. pro 复用原有密码登录及账号准入检查。仅对明确登记的内部客户端及允许的 scope 自动接续标准 OAuth 授权，其他客户端仍显示授权确认。BFF 请求成功后直接离开身份中心，不初始化 pro 工作台；授权失效时不得回退至 pro 工作台。
4. BFF 消费一次性的浏览器绑定登录事务，兑换授权码，调用身份中心 UserInfo。
5. 仅已启用的 BFF 成员建立会话。数据库只保存随机会话值的哈希及 AES-256-GCM 加密的令牌。
6. 同源写入同时验证 Origin 与会话 CSRF 值。会话最长七天，访问令牌按需在服务端刷新。当前服务按单进程运行，同会话刷新串行化。

pro 当前 JWKS 为空，采用 HS256。为保持现有会话签名配置，第一版采用 OAuth 2.1 email profile + UserInfo，不申请 openid。这里没有关闭 ID Token 验证，而是没有申请或消费 ID Token。

回调源站由 BFF 服务端 `BFF_ORIGIN` 配置，路径为 `/api/auth/callback`。Supabase OAuth 客户端负责登记和精确校验允许的回调，pro 页面仅消费 Auth 返回的有效授权详情和回调响应，不接受查询参数指定的任意返回域名。生产环境必须配置 HTTPS 源站，不允许缺省回到 localhost。本地和生产地址分别验证，实际生产域名部署时配置。

Supabase 的 OAuth scope 不等同于数据库权限隔离；OAuth access token 默认仍可能具有原用户对 pro 的数据权限。因此令牌只能存于受信任的 BFF 服务端，BFF 不向浏览器返回令牌，也不使用它操作 pro 业务数据。未来对第三方开放授权时需另行评估 client_id 的 RLS 约束。

## pro 的变更范围

新增 OAuth 授权 API、纯辅助函数、授权页面和公开框架路由。统一登录复用原登录表单，仅在有效 SSO 请求下接续 BFF；普通 pro 登录维持原有登录后初始化逻辑。新增 SSO 样式全部限定于对应页面类名，不更改普通 pro 登录布局。注册、找回密码与业务权限实现保持原有行为。

pro 工作区的其他改动属于其他工作，发布认证增量时必须隔离。已发现旧 Site URL（869123771.github.io）返回 404，GitHub Pages API 确认当前站点为 art-si.github.io。接入时修正默认 Site URL，并向 uri_allow_list 追加当前站点，保留所有旧允许地址。JWT 签名、注册策略及业务表保持原配置；配置调整前保留可恢复基线，并比较其他认证配置未被改变。
